# music-practice-tracker — guidance for Claude Code

Read this before working in `music-practice-tracker/`, a dependency-free browser SPA that randomizes and tracks progress through musical exercises (instrument → book → chapter → exercise range).

Unlike `d4cubeoptim/`, this app has **no external source repository** — it is authored directly in this repo, so edit the files here in place. There is no build step and no repo test runner; verify changes in a browser (see Testing below). Because it uses IndexedDB and ES-module `import`, it must be served over HTTP, not opened as `file://`: `python3 -m http.server 8000` from the repo root, then open `/music-practice-tracker/`.

## Architecture

Four files, plain ES modules, no framework:

- `index.html` — the whole UI shell + the details `<dialog>`. Loads exactly one script, `<script type="module" src="./app.js">`; `app.js` imports `db.js` itself (do not add a second script tag).
- `style.css` — styling only (light/dark via `prefers-color-scheme`).
- `db.js` — the IndexedDB data layer: constants, the document factory, and the optimistic-concurrency write helper. See its header comment.
- `app.js` — the controller: wires the DOM to `db.js` (autoload, randomize, checkbox, modal, throttled comment writes, the recency timer).

## Invariants you MUST preserve

1. **The database GUID is hardcoded and permanent.** `APP_GUID` in `db.js` is a fixed string; `DB_NAME = \`music-practice-tracker-${APP_GUID}\``. Never regenerate it at runtime. IndexedDB is per-origin and every app on `slaymaker1907.github.io` shares that namespace — the GUID exists solely to avoid colliding with *other* apps' databases. If you change the store shape, bump `DB_VERSION` and add an `onupgradeneeded` migration; do not rename the DB.

2. **One denormalized document per chapter.** A single object store `chapters`, keyPath `["instrument","book","chapter"]`, index `by_last_used_at`. All of a chapter's state — the shuffled `randomization`, `last_range`, `custom_list`, recency counters, and per-exercise `{completed, completed_at, comment}` under `exercises` — lives in that one document. This denormalization is deliberate; don't add stores or split it out without a strong reason.

3. **All writes go through `mutateChapter(key, expectedVersion, mutator)`.** It reads the doc, compares the integer `version` inside the same transaction, and on a match applies the mutator, increments `version`, and stamps `updated_at`; on a mismatch it throws `VersionConflictError` carrying the fresh doc. `app.js` wraps this in an `occ()` helper that adopts the fresh doc and retries once (per-field last-write-wins across tabs). Never call `store.put()` directly — route every new write through `occ()`/`mutateChapter`, or you break cross-tab concurrency safety.

    Exactly **three** functions in `db.js` bypass the version check, all deliberately. `deleteChapter(key)` removes the record regardless of version (invariant 11). `restoreChapter(key, resolver)` exists for Undo: a conflict has nothing useful to retry, because the snapshot Undo wants to write does not get "fresher". It is safe only because it hands the resolver the **live stored document** and the resolver is required to merge against it — never use it to write a document back verbatim. `replaceAllChapters(docs)` exists for Import (invariant 18) and is the same shape of exemption as `deleteChapter`: an imported file is the truth regardless of what is stored, and there is no per-document version to compare against anyway.

3a. **Undo is a merge, not a rewind.** `mergeRestore(before, after, live)` in `app.js` is a three-way merge, and its conflict rule is one line: **the other tab wins on anything it touched since the action; everything else reverts to the snapshot.** `after` (the document as it stood immediately after the action) is the base, so any field or exercise where `live` still equals `after` is untouched and safe to revert, while anywhere `live` has moved on another tab wrote it and keeps it. Presence counts as a value, so an exercise another tab added survives the undo and one it deleted stays deleted; `randomization` is the snapshot's order minus names that no longer exist, with surviving newcomers appended. The consequence is worth stating plainly: with a second tab active, Undo can produce a state that never previously existed (the pre-sort order back, but the other tab's newer checkbox still ticked). That is the intended outcome — it is the only option that both always lands and never silently discards concurrent work. `mergeRestore` and `sameValue` are pure and DOM-free, so they are the natural things to test in Node.

4. **Text edits are throttled to ≤1 write per 250ms** (leading write + guaranteed trailing flush), with an immediate flush on modal Save, on modal open, before either Randomize path, and on `visibilitychange → hidden`. Keep this; do not write on every keystroke. Two things make the throttle safe and must not be undone:
   - The throttle tracks **one** target exercise at a time, so `scheduleCommentPersist` flushes the previous target before retargeting. Without that, typing in row A then row B inside the same 250ms window silently discarded A's edit.
   - **Anything that removes a document must `await drainCommentWrites()` first.** Comment writes are fire-and-forget and their mutator does `doc = doc || newChapterDoc(...)`, so a write still in flight lands *after* the delete and resurrects the chapter. `chapter Delete` and `undoLast()` (which removes the document when undoing a create) both drain. This was invisible while Delete had a `window.confirm`: the blocking prompt gave in-flight writes time to land first, so removing the dialog is what exposed it. `cancelCommentThrottle()` is not enough — it drops *queued* edits but cannot recall a write already issued.
   - `pushUndo()` deliberately does **not** flush. `snapshotDoc()` overlays unpersisted comments onto the clone instead, so the snapshot is accurate without issuing a write at a record the caller may be about to delete. The paths whose mutator reads comments off the *stored* doc — both Randomize paths and the numbering rename — still call `flushComment()` explicitly before `pushUndo()`.
   - `occ()` carries **unpersisted comments across every `currentDoc` swap** via its `carry()` helper — on the write result *and* on the fresh doc adopted after a `VersionConflictError`. Docs coming back from IndexedDB only contain what is stored, so swapping one in verbatim wipes queued edits from memory, and the retry mutator (which reads `currentDoc`) then writes the blanks to disk. `pendingCommentNames` is the set `carry()` consults; names absent from the incoming doc are skipped so a deleted or dropped-from-range exercise never resurrects.

5. **Autoload has no button.** Typing a triple that matches a saved document loads it automatically. There is a race guard that ignores a stale `getChapter` result if the inputs changed during the `await` — preserve it when touching the input handlers.

6. **Recency timing.** `last_used_at` is bumped 60s after a *top-level* field change (instrument/book/chapter/min/max) or immediately on Randomize; comment and checkbox edits must never bump it. `use_count` bumps only on Randomize.

7. **A chapter is either range-driven or a custom list, and Randomize has one path for each.** Neither path confirms — the app has **no `window.confirm` calls at all** any more; Undo (invariant 10) is the safety net for every destructive action, which is why both paths call `pushUndo()` before their write. Both take the order they write, and the set of boxes they clear, from `randomizeOrder()` — never from a plain `shuffle()` — so the two-mode reset rule in invariant 16 is stated exactly once. Exercise identity is the string `exercise_name` (the map key doubles as the display label and supports non-numeric names with no migration).
   - **Contiguous** (`custom_list` falsy): rebuilds `exercises` from scratch to contain only the new min/max range's names — anything outside the new range is dropped entirely, comment included. `comment` **and `focus`** carry over on identical terms: only for names present in both the old and new range. Sets `last_range` and clears `custom_list`. `last_range` stores 1-based **indexes**, never spelled labels, so it stays meaningful across a change of numbering system (invariant 14). Because this path rebuilds the map, it must call `randomizeOrder()` **before** replacing `doc.exercises` — see invariant 16 for why asking afterwards inverts the answer.
   - **Custom** (`custom_list === true`, `last_range === null`): `reshuffleCustomList()` reorders the existing `randomization` in place. min/max are ignored; nothing is added or removed; **every comment and focus state is left untouched**. `custom_list` and `last_range` are unchanged. Since nothing is ever added here, `randomizeOrder()`'s "brand new name" tail is always empty on this path.

8. **`custom_list` is sticky and only one action clears it.** Adding or deleting a single exercise in Edit List mode sets `custom_list = true` and `last_range = null`. It stays true even if the surviving names happen to be contiguous again, and **Undo does not clear it**. The one way back is deliberate: enter Edit List mode (which re-enables the range inputs), type both min and max, and press Randomize — that takes the contiguous path above. A half-filled range is refused with an alert rather than guessed at. The field is absent on documents written before it existed, so always read it as `!!doc.custom_list`; that absence correctly means "contiguous", which is why this needed no `DB_VERSION` bump.

9. **Notes die in exactly two places.** A `comment` is destroyed only when (a) a contiguous Randomize drops that name out of the new range, or (b) the user deletes the row with its × in Edit List mode. No other path may lose one — in particular `deleteExercise` calls `discardPendingCommentFor(name)` so a throttled write in flight cannot re-create the record after the delete lands, and Undo of a delete restores the note verbatim from an in-memory snapshot.

10. **Edit List mode is UI-only and never persisted**, but the undo stack is no longer tied to it. `editMode` is reset by `resetEditState()` on page load, chapter switch, Reset Form, Delete, and every Randomize. `undoStack` is **not** — it is a global, in-memory, capped stack of whole-document snapshots that only a page load clears:
    - Entry shape is `{key, triple, before, after}`: `before` is the restore target (`null` = the chapter did not exist, so undoing removes it) and `after` is the merge base from invariant 3a (`null` = the action deleted the chapter). `pushUndo(key, triple)` takes `before` and stacks the entry immediately *before* the write; the call site sets `entry.after` once the write lands, and calls `popUndo(entry)` if it fails.
    - `pushUndo` calls `flushComment()` first. Without that, a note still queued behind the 250ms throttle sits outside the snapshot and the undo silently reverts something the user typed seconds ago.
    - Snapshots rather than per-action inverses, because every new undoable action used to need another hand-written inverse and Randomize has none expressible as a delta.
    - **The stack is global, not per-chapter.** Each entry carries its own triple, so `undoLast()` can reach into a chapter the user has navigated away from — and it refills the three inputs to navigate there, so the result is visible. That is what makes an undoable chapter Delete possible, and it is why leaving a chapter must *not* clear the stack.
    - Capped at `UNDO_LIMIT = 20`, oldest dropped, since each entry holds two full document clones.
    - Covers Sort, both Randomize paths, add/delete exercise, the numbering-system rename, and chapter Delete. It deliberately does **not** cover checkbox toggles or comment edits.

    Structural add/delete deliberately does **not** bump `last_used_at` (see invariant 6) — only `version`/`updated_at` advance. Deleting the final remaining row is blocked with an alert.

10a. **Sort rewrites `randomization` and nothing else.** `sortedOrder(doc, names)` orders by focus first (`focusRank`: focused before un-focused, invariant 16), then puts incomplete exercises before completed ones, each group ascending by the 1-based **index** `schemeOf(doc).parse(name)` returns — never by spelling, which is what puts `z` (26) before `a2` (27) and `IX` (9) before `X` (10). Names the scheme cannot parse have no index and settle at the end of their group alphabetically. The order is computed **inside** the `occ()` mutator from the mutator's own doc so an OCC retry converges on the correct state rather than replaying a stale array. Sort touches neither `custom_list`, `last_range`, completion, comments, focus states, nor the recency counters, and it is always available — it is not an Edit List mode control.

11. **Reset Form (button id `clear-btn`) is a UI-only reset** — it clears inputs and the visible list and deletes nothing; re-entering the triple autoloads the saved document back. **Delete** (`#delete-btn`) is the destructive counterpart — it removes the chapter document via `deleteChapter(key)` in `db.js`, which intentionally bypasses `mutateChapter`'s OCC check (delete removes whatever is stored regardless of version), then resets the form the same way. It no longer confirms: `pushUndo()` runs first with `entry.after = null`, so Undo puts the chapter back *and* navigates to it. Note the limit honestly — the stack is in-memory, so a reload between the delete and the undo does make it permanent.

12. Triple values are **trimmed** before they key/persist a document, so `"Piano "` and `"Piano"` collapse to one record. Keep keying consistent with this.

13. **instrument → book → chapter is a hierarchy.** Editing an ancestor field (typing, a datalist pick, or its `#…-clear` × button) clears every descendant field immediately — instrument clears book+chapter, book clears chapter. An incomplete triple always clears `currentDoc`, the exercise list, and the progress counter (see `autoload()`'s early-return branch) so no stale chapter is left on screen.

14. **A numbering system is a codec, not a data model change.** `doc.numbering_system` is one of `"numbers"`, `"letters-upper"`, `"letters-lower"`, `"roman"`; the `NUMBERING` table in `app.js` gives each one a `label(n)` (1-based index → name) and a `parse(s)` (name → index or `null`). Rules to keep:
    - **`parse()` must return `null` for anything the scheme does not own.** That tolerance is what lets a list still holding names minted under a different scheme keep working — unparseable names are skipped when choosing the next one, exactly as non-numeric names always were. The letter schemes reject the wrong case and mixed runs like `"ab"`; `roman` validates by re-encoding and comparing, so `"IV"` and `"MMMM"` parse but `"IIII"` and `"IC"` do not.
    - **The field is absent on older documents and reads as `"numbers"`** (`schemeOf()` also falls back for unrecognized values), which is why this needed no `DB_VERSION` bump or migration. Do not "upgrade" old docs by writing the field into them on read.
    - **Changing the system renames the whole chapter.** `buildRenameMap(names, from, to)` maps every name the *outgoing* scheme parses to the *incoming* scheme's spelling at the same index (`1`↔`a`, `2`↔`b`, `9`↔`IX`), and `onNumberingChanged` rebuilds `exercises` under the new names and maps `randomization` through it, so completion state, comments, and list order all follow their exercise. `last_range` holds indexes and needs no translation, but `#min`/`#max` must be re-spelled with `populateRange()` afterward — `applyNumberingSystem()` blanks them when the digits it finds no longer parse, and leaving them empty would make Randomize refuse the chapter it was just describing. The rename is undoable and unconfirmed like every other write action.
      - Names the **old** scheme cannot parse have no index to carry across and keep their name, so a mixed-scheme list is still a legitimate state.
      - Renames that would collide are dropped rather than guessed at: switching a list holding both `1` and `a` from letters to numbers would map `a`→`1` on top of the retained `1`, so `a` stays `a`. Names that are *moving* vacate their spelling first, so `1`→`a` can take `a` when `a` is itself becoming `b`. `buildRenameMap` is pure and returns only the entries that actually change; it is worth testing in Node alongside the codec.
      - Re-derive the map **inside** the `occ()` mutator from the mutator's own doc: on a retry the fresh doc may hold names this tab never saw, and they need renaming too.
    - **Only the letter schemes put `#min`/`#max` into text mode** (`scheme.textInput`). Roman numerals are entered as ordinary digits — 1 and 5 build I through V — because typing `"IV"` into a range box is far more error-prone than typing `4`. `syncNumberingInputs()` owns the retyping and clears a value that no longer parses.
    - **The UI selection wins over the stored field.** `addExercise()` and the contiguous Randomize both stamp `doc.numbering_system = numberingSystem` *before* deriving names, so the select reflects intent even if its own persist write has not landed.
    - **A letter scheme past one alphabet appends a numeral, not another letter.** `letterLabel(n, alphabet)` spells 1–26 as `a`–`z`, then 27–52 as `a2`–`z2`, 53–78 as `a3`–`z3`, and so on; `letterParse()` accepts a bare letter or a letter followed by an integer ≥ 2 (`"a1"` is invalid — index 1 is already `"a"`). An earlier version of the app spelled this range by doubling the letter instead (`"aa"`, `"bb"`, `"aaa"`, …); see invariant 19 for how that gets migrated away. `legacyLetterParse()` recognizes only that old doubled shape and is never used by `letterLabel()`/`letterParse()` — it exists solely for the migration.
    - **`#numbering-hint` spells the wrap out, because the select can't.** Nothing in `<option>` text like `"a, b, c"` hints that index 27 is `"a2"` rather than another letter, so `syncNumberingInputs()` fills `#numbering-hint` with `scheme.wrapHint()` for `letters-upper`/`letters-lower` and empties it (CSS `:empty` hides the element) for `numbers`/`roman`, which never wrap into anything non-obvious. `wrapHint()` is generated from `letterLabel(27|28|53, alphabet)` rather than hardcoded text, so it cannot drift from the actual spelling if that ever changes again.

15. **New exercise names fill gaps before extending.** `nextExerciseName(doc)` collects the indexes it can parse, then returns the lowest free index between the smallest and largest present, falling back to `max + 1` only when that span is saturated (an empty or wholly-unparseable list starts at index 1). A trailing loop still walks forward until the label is genuinely free. This must stay **inside** the `occ()` mutator: gap-filling makes two tabs picking the same name *more* likely than plain `max+1` did, and only re-deriving from the fresh doc on retry keeps names unique.

16. **Focus is binary, and it is what decides how much a Randomize resets.** Each record in `exercises` may carry `focus`, either `"focused"` or (by absence) normal. The focused set is the *practice rotation*: the work you want back in front of you every session. Rules to keep:
    - **Read it only through `focusOf(doc, name)`, which treats absent — and any value it does not recognize — as `"normal"`.** The field is missing from every pre-feature document *and* from every exercise nobody has focused, because writes omit it when it is the default: `setFocus()` `delete`s the key rather than writing `"normal"`, and `onResetFocus()` does the same across the whole chapter. That absence is why this needed no `DB_VERSION` bump or migration, exactly like `custom_list` and `numbering_system`.
    - **That same tolerance is what retired the old third state.** Focus used to be three-way, with `"paused"` meaning shelved-but-not-deleted. `FOCUS_RANK` no longer lists it, so `focusOf()` reads a leftover `focus: "paused"` record as plain normal and **there is nothing to migrate** — no on-load backfill, no `DB_VERSION` bump, no cleanup pass. A stale value disappears for real the next time that exercise is toggled or Reset Focus runs. Do not add a migration for this; the absence rule already covers it.
    - **`randomizeOrder(doc, names, prevOrder)` is the single definition of both the order and the reset scope**, and both Randomize paths call it. It returns `{ full, order }` in two modes, switched on `anyFocusedCompleted(doc)` — literally "is any focused box ticked right now", a read of current state with nothing extra persisted:
      - **FULL** (no focused box ticked): clear *every* box, reshuffle everything, focused block on top. Note the vacuous case is load-bearing — a chapter with **nothing focused** has no focused box that could be ticked, so it always lands here and therefore behaves exactly as Randomize did before focus existed. That is the compatibility guarantee; do not "fix" it.
      - **PARTIAL** (at least one focused box ticked): the focused set clears and reshuffles to the top, and everything un-focused is left **strictly alone** — same ticks *and* the same relative order it already had. The un-focused block is never shuffled in this mode. Names brand new to the chapter (a widened range) have no previous position, so they land after the un-focused block in the order `names` supplies.
    - **Ask `randomizeOrder()` BEFORE clearing anything.** A partial reset clears exactly the focused ticks, so re-asking afterwards always answers `full` and silently inverts the decision. The contiguous path must therefore call it before it replaces `doc.exercises`, and the custom path before its clear loop. This is the single easiest way to break this feature.
    - **A known, accepted consequence:** because the switch reads current state, pressing Randomize twice in a row does a full clear the second time — the first press left no focused box ticked. Undo covers it. This was a deliberate choice over persisting a "practiced since last randomize" flag.
    - **It changes the order, never the set.** Nothing is ever hidden, skipped, or dropped for being un-focused. Sort reuses the same ranking via `focusRank` as its leading key (invariant 10a).
    - **The progress counter counts every exercise on screen**, so the fraction can never contradict the visible list, and appends `· N focused` to name the size of the rotation a Randomize would reset.
    - **The toggle is on every row at all times** — not gated behind Edit List mode like `.ex-delete`. Choosing the rotation is ordinary practice and it steers Randomize, so burying it made the most consequential control the hardest to reach. Dropping the `"Exercise "` prefix from `.ex-name` is what paid for the width.
    - **The per-exercise toggle is not undoable; Reset Focus is.** One press flips in or out of the rotation and is treated like the completion checkbox — cheap, visible, reversed by pressing again — so it never calls `pushUndo()` and would otherwise push genuinely destructive entries off the capped stack. `#reset-focus-btn`, which rewrites every exercise at once, *does* `pushUndo()`, and like every other write action it does not confirm.
    - **Focus writes are serialized** through `queueFocusWrite()`, and `setFocus()` updates `currentDoc` + the DOM *before* awaiting. Both matter: sweeping down the list toggling several rows is normal use, and without the queue the third overlapping write exhausts `occ()`'s single retry and loses, while without the optimistic update each press re-reads the same pre-write state and resolves to the same next state.
    - **Undo needs no special handling.** `mergeRestore()` compares whole exercise records with `sameValue`, so `focus` rides along with completion and comments for free. `modalSnapshot` must keep carrying it, though — see invariant 17.

17. **`modalSnapshot` must hold every field of an exercise record.** `revertModal()` writes `{ ...modalSnapshot }` as the *whole* record, so any field missing from the snapshot is erased by a Cancel or an Esc, not merely left alone. It currently holds `completed`, `completed_at`, `comment` and `focus`; add to it whenever you add a per-exercise field. The revert is deliberate for changes made *inside* the modal (a focus cycled there is undone by Cancel, exactly as the checkbox is) — what would be a bug is a state set *before* opening quietly reverting to the default.

18. **Export/Import move the WHOLE store, and Import replaces it.** IndexedDB is per-device, so this is the only sync between a phone, a tablet and a laptop. There is no merge: whichever device you export from wins, and a chapter deleted there disappears on import. The rules:
    - **`replaceAllChapters(docs)` does `clear()` + N × `put()` in ONE transaction**, so an import is atomic — either the whole new database lands or the old one is untouched. It is the third OCC bypass (invariant 3). Documents are stored with the `version` values the file carries, so another tab's next OCC write conflicts and re-reads rather than clobbering the import.
    - **Both operations flush and drain comment writes first**, for two different reasons. On Export a note typed in the last 250ms is still behind the throttle and would be missing from the file. On Import it is invariant 4's resurrection hazard in its sharpest form: a fire-and-forget comment write whose mutator does `doc = doc || newChapterDoc(...)` lands *after* `clear()` and re-creates a chapter the imported file does not contain. Import **flushes** rather than cancels, deliberately — the file is validated *after* the preamble, so cancelling would discard a real note even when the import is then rejected.
    - **Validation is complete before anything is written.** `parseImportPayload()` is pure and throws user-facing messages; a rejected file leaves the database bit-for-bit unchanged. It checks `format`, `app_guid` against `APP_GUID`, `db_version`, that `chapters` is an array, and that every entry has string `instrument`/`book`/`chapter` (a non-string would make `put()` throw mid-transaction and abort the import) plus an object `exercises`.
    - **The `db_version` check is one-sided on purpose.** A *newer* file is refused, because it may hold a shape this build cannot read and importing it looks like corruption. An *older* one is accepted, because invariants 8, 14 and 16 all define absent as the default — an old export is exactly a document missing `custom_list` / `numbering_system` / `focus`.
    - **`swapDatabase()` wipes `undoStack`.** Entries hold per-chapter snapshots whose `version` was meaningful against the *old* database, and whose chapters may not exist in the new one; since `restoreChapter` has no version check, an Undo pressed after an import would write a document from the previous database over the imported one. It also clears `currentDoc`, `pendingCommentNames`, the modal state and edit mode, then rebuilds the view through `loadMostRecentChapter()`.
    - **`importBackup` is NOT an undo-stack entry.** The stack is per-chapter (`{key, triple, before, after}` merged by `mergeRestore`) and a whole-store replace has no representation there, so Import gets its own snapshot and its own `#undo-import-btn`. It is one-shot (cleared after use) and in-memory only, so a reload makes an import permanent — the same honest limitation invariant 11 notes for Delete. This snapshot is what lets Import skip a confirmation dialog and keep invariant 7's "no `window.confirm` anywhere" intact.
    - **`loadMostRecentChapter()` is shared by startup and both swaps** and must handle an empty store (an import of a file with zero chapters) by clearing the form the way `onClearForm()` does. Do not let it assume a document exists.
    - Export prefers `navigator.share({files})` when `navigator.canShare` accepts it — on iOS that is the only convenient way to get the file to another device — and falls back to `Blob` + `<a download>`. A share dismissed with `AbortError` must **not** then fire the download; the user declined.

19. **The old doubled-letter spelling is backfilled away on load, not on read.** A letters chapter written before `letterLabel()` switched from doubling (`"aa"`, `"bb"`, `"aaa"`) to a numeral suffix (`"a2"`, `"b2"`, `"a3"`) gets its exercise names re-spelled the moment it is loaded — `backfillLetterNumberingIfNeeded()` runs after every chapter load (`autoload()`, `loadMostRecentChapter()` — which covers startup, Import and Undo Import — and `undoLast()`). Rules to keep:
    - **The migration itself, `backfillLetterNumbering(doc)`, is pure** and reuses `buildRenameMap()` (invariant 14) with a `legacyLetterParse`-based "from" scheme and the real scheme's `label()` as the "to" — the exact same collision-avoidance and index-preserving logic a numbering-system change gets, because this is that same shape of rename, just from an old spelling of the *same* system to its current one. It returns `null` when there is nothing to migrate, which is the common case on every load after the first.
    - **It is silent and not undoable.** Nothing is lost — every name maps 1:1 to the same index, carrying completion, comment and focus with it — so unlike a user-initiated numbering change this needs no `pushUndo()` entry; it is a transparent migration, not an edit. For the same reason it must **not** touch `last_used_at` or `use_count`.
    - **The rename map is re-derived inside the `occ()` mutator**, like the numbering-system rename and `nextExerciseName()`, so a retry against a fresher doc (or one another tab already migrated) still converges correctly.
    - **A queued comment write is flushed before the rename**, for the same reason invariant 18's Import preamble and `onNumberingChanged` both flush first: `occ()`'s `carry()` only re-applies a pending comment to a name still present in the incoming doc, and the rename moves that exercise to a new key.
    - **`letterBackfillInFlight` dedupes concurrent calls for the same triple.** Two DOM events for one still-unmigrated chapter (a keystroke's `input` plus a later blur's `change`, both routed through `autoload()`) would otherwise each start their own `occ()` write; a second write is harmless (it just finds nothing left to migrate and writes the doc back unchanged) but wasteful, so the second caller awaits the first's promise instead of starting its own.
    - **Not awaited by any call site** — the chapter renders immediately with whatever names it loaded with, and `renderList()` runs again only if the migration actually changed something and the user is still looking at that chapter (`tripleEq` guards against a switch or delete mid-write, mirroring the guard `autoload()` already uses for races).

## DOM contract (keep `index.html` and `app.js` in sync)

Inputs `#instrument #book #chapter` (+ datalists `#instrument-list #book-list #chapter-list`, + per-field reset buttons `#instrument-clear #book-clear #chapter-clear`), `#min #max` (both retyped between `number` and `text` by `syncNumberingInputs()`) and the `#numbering` `<select>` with its `#numbering-hint` (filled in for the letter schemes only, `:empty`-hidden otherwise — see invariant 14), buttons `#randomize-btn #clear-btn #undo-btn #reset-focus-btn #delete-btn` (Undo sits in the form's `.actions` bar, not the list toolbar, because it now reverses Randomize, Reset Focus and chapter Delete too; it is `disabled` whenever the stack is empty. `#reset-focus-btn` sits immediately before Delete and puts every exercise back to normal in one undoable, unconfirmed write), `#progress-counter`, the list toolbar `#list-actions` (`.hidden` when no list, `.edit-mode` when editing) holding `#edit-list-btn` (labeled "Edit List" when off and "Exit Edit" while editing — `setEditMode()` swaps `textContent`, and `.editing` adds the active color), `#sort-btn` (always visible), and `#new-exercise-btn` (the only button the `.list-actions:not(.edit-mode)` rule in `style.css` hides), then `#exercise-list` (also carries `.edit-mode`), the data panel `#data-panel` (a `<details>` that starts collapsed; `#export-btn #import-btn #undo-import-btn` share one `.data-actions` row, `#import-file` is a `.visually-hidden` file input that `#import-btn` clicks, and `#data-status` carries success text — failures still go through `showError()`), and the modal `#details-modal` with `#modal-title #modal-check #modal-focus-slot #modal-focus-label #modal-comment #modal-save #modal-cancel`. Rows are built in `app.js` as `.exercise-row` (+ `.completed`) containing `.ex-check`, `.ex-name` (**just the name — no `"Exercise "` prefix**), `.ex-oneline`, `.ex-details`, `.ex-focus`, and `.ex-delete`. Only `.ex-delete` is edit-mode-gated: it is built on every row but shown only under `#exercise-list.edit-mode`, so toggling edit mode is a pure CSS change and never re-renders. `.ex-focus` is visible always (invariant 16).

Icons and focus state:
- `.ex-details` and `.ex-delete` are **icon-only** — `app.js` fills each with an inline SVG from its `ICONS` table (`expand` / `close`) and the text lives in the `aria-label`. Those literal SVG strings are the only thing this app ever assigns to `innerHTML`; never put document content there.
- `.ex-focus` (rows) and `.focus-toggle` (modal) are the same control, both built by `buildFocusToggle()`: one button holding a `.focus-icon-focused` bullseye. `data-focus` on the button lights the bullseye green when it is `"focused"` and leaves it dim-but-legible otherwise — that dim state is the only advertisement of what a press would do, so never ghost it. `data-focus` on `.exercise-row` additionally accents focused rows down the left edge. `markFocusToggle()` stamps `data-focus`, `aria-pressed` (the honest semantic now that focus is binary) and the `aria-label` together; `syncRowFocus(name)` is the single writer of all of that, including `#modal-focus-label`.
- The modal's copy is appended into the empty `#modal-focus-slot` by `wireEvents()` rather than written in `index.html`, because `buildFocusToggle()` needs the `ICONS` table that is initialized further down the module.

`.ex-oneline` is directly editable (typed edits go through the same 250ms throttle as the modal) whenever the comment is single-line or empty; it becomes `[readonly]` once the comment is multi-line, and clicking it while locked (or clicking `.ex-details` regardless of lock state) opens the modal. **"Multi-line" is `isMultiline()`, not `includes("\n")`**: a newline only counts if non-whitespace follows it, so pressing Enter at the end of a line in the modal — or leaving a trailing blank line — does not lock the row box. The modal's `input` handler calls `refreshRowPreview()` on every keystroke so the row box mirrors the textarea live and unlocks/relocks as the content crosses that boundary; `refreshRowPreview()` skips assigning `.value` when that input is `document.activeElement`, or it would jump the caret of someone typing in the row itself. Change an id/class in one file and you must change it in both.

## Testing

No repo test runner. Serve locally and check the full flow by hand or with a headless-Chromium script: Randomize a range → tick some checkboxes → add a multi-line comment in the modal → reload and confirm everything persisted → open a second tab on the same chapter and confirm concurrent edits both survive (the OCC path). Also check: typing directly into a row's one-line box persists without opening the modal; a comment that gains a second line in the modal locks the row box on save; re-randomizing an overlapping range clears all checkboxes chapter-wide, drops exercises outside the new range, and keeps comments for exercise names still in range; Delete removes the IndexedDB record and clears the form. Inspect Application → IndexedDB in DevTools to confirm there is exactly one `chapters` store and that `version` advances on writes.

For the custom-list feature specifically, also check: Edit List reveals the × and New Exercise controls without re-rendering (and the button itself now reads "Exit Edit"); New Exercise prepends the lowest free name — delete 2 and 4 out of 1–5, then add three times, and expect `2`, `4`, `6`; deleting a row sets `custom_list` and leaves min/max blank + greyed (and still greyed after reload); Undo steps back through several adds/deletes, restoring deleted rows at their original position with their notes; the last remaining row cannot be deleted; Randomize on a custom list reshuffles without changing the exercise set or any note; entering Edit List mode, typing a full range, and pressing Randomize returns the chapter to contiguous numbering. Two tabs adding an exercise concurrently must not produce duplicate names — that is why `addExercise()` computes the name *inside* the mutator, where an OCC retry re-derives it from the fresh doc.

For the numbering systems, check each of the four: New Exercise mints the right spelling; picking a letter scheme turns `#min`/`#max` into text boxes that take `a`–`f` while Roman keeps numeric boxes where 1–5 builds I–V; a range past `z` appends a numeral (`a2`, `b2`, … `z2`, then `a3`); the selection survives a reload from `numbering_system`; and a document with no `numbering_system` field still loads as plain numbers. For the rename: a chapter of `1`–`12` switched to `letters-lower` becomes `a`–`l` with every checkbox, comment, and list position following its exercise, and the range boxes re-spell as `a`/`l` rather than blanking; Undo reverts the names, the range, and the select together; a list holding both `1` and `a` refuses the colliding rename and keeps both names.

For the letter-numbering backfill (invariant 19): in DevTools, hand-write a `letters-lower` chapter whose `exercises`/`randomization` use the old doubled spelling (`a`, `aa`, `bb`, `aaa`, with a comment and a focus mark on a couple of them), then type its triple into the form. The list must show `a2`, `b2`, `a3` in place of `aa`, `bb`, `aaa`, with every comment, checkbox and focus mark intact and the order otherwise unchanged; reload and confirm the new spelling persisted (`version` advanced by exactly one, not two); confirm `#undo-btn` stays disabled — this migration must never be undoable. Repeat by leaving that chapter as the most-recently-used one and reloading the page cold (exercises `loadMostRecentChapter()` instead of `autoload()`), and again via Undo (restore a snapshot that still holds doubled names). Check `letters-upper` migrates the same way (`AA`→`A2`). A name the old scheme can't parse (e.g. a hand-added `"warm-up"`) must keep its name. A collision — both `aa` and `a2` already present — must leave `aa` alone rather than overwrite `a2`.

For Sort: Randomize 1–12, tick 3/7/11, press Sort, and expect `1 2 4 5 6 8 9 10 12 3 7 11`; check `z` lands immediately before `a2` under a letter scheme and `IX` before `X` under Roman; reload and confirm the order persisted.

For Undo: it is enabled after any of the six covered actions and disabled after a reload; undoing a Randomize brings back the previous exercise set, order, checkboxes, and comments; undoing a chapter Delete restores the record *and* refills the triple; undoing a Randomize that created the chapter removes it from IndexedDB and from the datalists; the stack survives a chapter switch and a Reset Form, and undoing then navigates back to the original chapter. The merge needs two tabs: sort in tab A, then in tab B tick one exercise, comment on another, and add a third — Undo in tab A must restore the pre-sort order while keeping all three of tab B's edits.

For focus states: the toggle must be pressable **without** entering Edit List mode, while the delete × must still be hidden until you do. Press a row's toggle twice and watch it light and go dim again, then reload and confirm it persisted. Press one three times *rapidly* — every press must land (that is the `queueFocusWrite` + optimistic-update pair; without either, the row snaps back). Confirm rows read `12`, not `Exercise 12`, and that a stored record for a never-focused exercise has **no** `focus` key at all. Check the counter reads `N of 10 complete · 3 focused` and drops the suffix when nothing is focused. Reset Focus empties the rotation with no dialog and leaves no `focus` key behind; Undo brings every prior state back. Open the modal on a focused exercise, edit the comment, press Esc, and confirm it is *still* focused (invariant 17). Sort with a mix: expect focused-incomplete, focused-complete, un-focused-incomplete, un-focused-complete, each ascending by index. Finally, hand-write a record with `focus: "paused"` in DevTools and confirm it simply loads as un-focused — that is the retired third state, and it must need no migration.

For the two Randomize modes (invariant 16), which is the part most worth driving by hand:
- **Nothing focused** → every Randomize is a full clear and reshuffle, exactly as before the feature existed. Tick a few, Randomize, confirm all boxes cleared.
- **Focused but none of them ticked** → still a full clear. Focus 1 and 2, tick only un-focused 5 and 7, Randomize: 5 and 7 must come back *un*ticked.
- **At least one focused ticked** → partial. Focus 1 and 2, tick 1 plus un-focused 5 and 7, Randomize: 1 and 2 clear and move to the top; 5 and 7 stay ticked; and the un-focused block must appear in the **exact same relative order** it had before — run it several times and confirm that tail never permutes.
- **Widened range mid-rotation** → with a partial armed, change max from 8 to 11: the surviving un-focused block keeps its order and ticks, and 9/10/11 appear after it.
- **Double press** → immediately Randomize again after a partial and confirm it *does* full-clear (the accepted consequence), and that Undo restores the un-focused ticks.
- Repeat the partial case on a **custom list** (blank min/max) and confirm the exercise set, comments and `custom_list` are all untouched.

For the one-line comment box: open the modal on an empty comment and type a single line — the row box below must mirror it live and stay editable; press Enter and confirm it is still editable; type a real second line and confirm it locks; delete that line and confirm it unlocks. Type directly into a row box and confirm nothing steals the caret.

For export/import: build a couple of chapters with mixed state (a custom list, a non-default numbering system, a focused exercise, a multi-line comment, some checkboxes) and Export — the file's `chapters` array must be byte-identical to what the store holds, `version` included. Then add a third chapter and import the old file: the third chapter must be **gone** (replace, not merge), `#undo-btn` must be disabled (the stack was wiped), and Undo Import must put all three back and then disable itself. Feed it bad input — non-JSON, a JSON object with no `format`, a foreign `app_guid`, `"db_version": 99`, a non-array `chapters`, a chapter whose `chapter` is a number, a chapter with no `exercises` — and confirm each shows a distinct message and leaves every stored `version` untouched. Strip `custom_list`, `numbering_system` and every `focus` from an export and confirm it imports as contiguous / numbers / all-normal. Import `"chapters": []` and confirm the form, list, counter and datalists all empty out without throwing. Reload and confirm Undo Import starts disabled.

The two throttle cases are the ones most likely to break and the least likely to be noticed: type into a row's one-line box and press Export **within 250ms** — the file must hold the newest keystrokes, not the leading-edge write; and type into a row of chapter X, then immediately import a file that does not contain X — X must not reappear (invariant 18's resurrection hazard).

The pure functions are worth testing directly in Node — `NUMBERING`, `schemeOf`, `letterLabel`, `letterParse`, `legacyLetterParse`, `backfillLetterNumbering`, `nextExerciseName`, `sortedOrder`, `focusOf`, `nextFocus`, `partitionByFocus`, `anyFocusedCompleted`, `randomizeOrder`, `isMultiline`, `buildRenameMap`, `sameValue`, `mergeRestore`, `buildExportPayload`, and `parseImportPayload` touch neither the DOM nor IndexedDB, so they can be sliced out of `app.js` and asserted on as plain objects. `randomizeOrder` earns close attention: assert that the partial mode's un-focused tail is byte-identical across many runs (it must never be shuffled), that no name is ever dropped or duplicated in either mode, and that the vacuous no-focus case answers `full`. `mergeRestore` deserves the most attention there: its two-tab cases are tedious to drive by hand and trivial to assert on directly. `parseImportPayload` is next — every branch is a rejection that protects the whole database, and each one is a two-line assertion. `backfillLetterNumbering` is worth a round-trip check too (`letterParse(letterLabel(n)) === n` for a wide range of `n`) plus the collision case, since it is the one migration in this codebase that runs without the user asking for it.
